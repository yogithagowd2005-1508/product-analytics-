# 15 — WORK PACKAGE N: DEVELOPER ANALYTICS HANDOFF SPECIFICATION

> **MANDATORY DATA AUTHENTICITY NOTICE**  
> *VELOOP is a real product under development, but the data supplied and evaluated for this assignment is fictional/simulated for analytical testing. In accordance with the Data Authenticity Policy, no metric or finding herein represents actual VELOOP production statistics, actual earnings, actual withdrawals, or live business performance.*

---

## 1. Engineering Executive Mandate
The **Developer Analytics Handoff (Work Package N)** provides backend engineers, mobile app developers, and QA automation engineers with explicit, testable, and unambiguous implementation specifications for the platform's mission-critical telemetry events.

Every specification includes:
- **Requirement ID & Priority**: Tracked in Jira / GitHub Issues.
- **Trigger Condition**: Exact client or server state transition.
- **JSON Payload Contract**: Strict attribute types, nullability, and regex validation rules.
- **Deduplication & Idempotency Key**: Protocol to eliminate duplicate processing.
- **Acceptance Test**: Concrete QA test criteria required for pull request approval.

## 2. Critical Event Engineering Specifications

### Specification DEV-EVT-001: `account_user_registered`
- **Requirement ID**: `REQ-ANALYTICS-001`
- **Priority**: Critical
- **Event Name**: `account_user_registered`
- **Trigger**: New user completes signup credentials or OAuth authentication handshake and profile row commits to the database.
- **Event Source**: Backend Auth Service / API Gateway
- **Why Needed**: Establishes user acquisition baseline, cohort birthdate, and marketing attribution denominator.
- **KPI Dependency**: New Registrations, CAC by Channel, Onboarding Funnel Conversion.
- **Timestamp Standard**: UTC ISO 8601 (`YYYY-MM-DDTHH:MM:SS.sssZ`) generated by auth server clock.
- **Deduplication Strategy**: Enforce database uniqueness constraint on `user_id` and client idempotency `event_id`.
- **Payload Schema**:
```json
{
  "event_id": "8f3a19b2-3e41-4c92-b52e-72b1a09d31f4",
  "event_name": "account_user_registered",
  "timestamp": "2026-03-15T10:22:15.120Z",
  "user_id": "USR_00001",
  "device_platform": "Android",
  "country_code": "US",
  "properties": {
    "registration_source": "referral",
    "acquisition_campaign": "summer_boost",
    "referral_code": "VELOOP_VIP_99",
    "device_model": "Pixel 8",
    "os_version": "14.2.1"
  }
}
```
- **Field-Level Validation**:
  - `user_id`: String, Mandatory, Regex `^USR_[0-9]{5}$` or UUID v4.
  - `registration_source`: Enum, Mandatory, `IN ('organic', 'referral', 'paid_ad', 'partner_promo', 'influencer')`.
  - `device_platform`: Enum, Mandatory, `IN ('Android', 'iOS', 'Web')`.
  - `country_code`: String, Mandatory, ISO 3166-1 alpha-2 uppercase (`^[A-Z]{2}$`).
- **Acceptance Test**:
  > *When a new user successfully registers, exactly one `account_user_registered` event must be emitted and persisted to the raw event store within 500ms. If the client retries the network request with the same `event_id`, the API gateway must return HTTP 200 without emitting a second database record.*

### Specification DEV-EVT-002: `task_started`
- **Requirement ID**: `REQ-ANALYTICS-002`
- **Priority**: Critical
- **Event Name**: `task_started`
- **Trigger**: User explicitly clicks "Start Task" or rewarded video stream initializes.
- **Event Source**: Client Mobile SDK & Task Gateway
- **Why Needed**: Measures task catalog demand, initiation volume, and serves as denominator for task completion rate.
- **KPI Dependency**: Task Start Volume, Task Completion Rate, Abandonment Velocity.
- **Timestamp Standard**: UTC ISO 8601 recorded at the moment task modal or video opens.
- **Deduplication Strategy**: Ephemeral UUID v4 assigned to `task_activity_id`.
- **Payload Schema**:
```json
{
  "event_id": "2b819f03-6e11-4a82-9381-01f82a93c120",
  "event_name": "task_started",
  "timestamp": "2026-04-01T12:00:00.050Z",
  "user_id": "USR_00001",
  "session_id": "SES_123456",
  "device_platform": "Android",
  "properties": {
    "task_activity_id": "TSK_000100",
    "task_id": "TK_AD_101",
    "task_type": "watch_ad",
    "partner_provider": "GoogleAdMob",
    "potential_reward_amount": 15.00,
    "reward_unit": "VEs"
  }
}
```
- **Field-Level Validation**:
  - `task_activity_id`: String, Mandatory, Unique execution ID (`^TSK_[0-9]{6}$`).
  - `task_type`: Enum, Mandatory, `IN ('watch_ad', 'survey', 'tap_earn', 'mining', 'offerwall', 'app_install')`.
  - `potential_reward_amount`: Numeric, Mandatory, Strictly `> 0`.
- **Acceptance Test**:
  > *Initiating any earning task must generate a unique `task_activity_id` and publish a `task_started` record before launching external provider SDK activities. Rapid double-tapping the button must be debounced by the client UI (500ms lockout).*

### Specification DEV-EVT-003: `task_completed`
- **Requirement ID**: `REQ-ANALYTICS-003`
- **Priority**: Critical
- **Event Name**: `task_completed`
- **Trigger**: User fulfills task requirements and partner S2S postback or internal validator confirms completion.
- **Event Source**: Backend Validation Engine / Partner Webhook Proxy
- **Why Needed**: Verifies earning fulfillment; serves as the prerequisite verification signal for reward issuance.
- **KPI Dependency**: Completed Tasks, Task Completion Rate, Partner Reliability.
- **Timestamp Standard**: UTC ISO 8601 recorded at validation confirmation.
- **Deduplication Strategy**: Enforce database uniqueness constraint on `task_activity_id`.
- **Payload Schema**:
```json
{
  "event_id": "9c12a84e-5b23-41f9-9021-3e41b901a882",
  "event_name": "task_completed",
  "timestamp": "2026-04-01T12:00:30.450Z",
  "user_id": "USR_00001",
  "session_id": "SES_123456",
  "device_platform": "Android",
  "properties": {
    "task_activity_id": "TSK_000100",
    "task_id": "TK_AD_101",
    "task_type": "watch_ad",
    "reward_amount": 15.00,
    "reward_unit": "VEs",
    "duration_seconds": 30,
    "validation_status": "validated",
    "partner_provider": "GoogleAdMob",
    "partner_transaction_id": "ADMOB_TX_881923"
  }
}
```
- **Field-Level Validation**:
  - `task_activity_id`: String, Mandatory, Must match an existing `task_started` record.
  - `duration_seconds`: Integer, Mandatory, Must exceed minimum task duration threshold (e.g. `>= 15` for video ads).
  - `validation_status`: Enum, Mandatory, Must equal `'validated'`.
- **Acceptance Test**:
  > *When a valid task completion occurs, exactly one analytically usable completion event should be recorded for the relevant task/user transaction, subject to the final engineering implementation and idempotency design. If verification fails, a `task_failed` event must be emitted instead.*

### Specification DEV-EVT-004: `reward_credited`
- **Requirement ID**: `REQ-ANALYTICS-004`
- **Priority**: Critical
- **Event Name**: `reward_credited`
- **Trigger**: Rewards engine writes a positive balance increment to the double-entry accounting ledger.
- **Event Source**: Core Ledger Service
- **Why Needed**: Authoritative financial liability creation event; tracks monetary points issued to users.
- **KPI Dependency**: Total Reward Issuance, Gross VE Supply, ARPAU.
- **Timestamp Standard**: UTC ISO 8601 recorded by ledger database commit.
- **Deduplication Strategy**: Enforce database primary key on `reward_id` and unique foreign key on `task_activity_id`.
- **Payload Schema**:
```json
{
  "event_id": "4a18c091-1d22-48a3-8109-7e21a091f339",
  "event_name": "reward_credited",
  "timestamp": "2026-04-01T12:00:32.100Z",
  "user_id": "USR_00001",
  "device_platform": "Android",
  "properties": {
    "reward_id": "RWD_00001",
    "task_activity_id": "TSK_000100",
    "reward_type": "task_completion",
    "amount": 15.00,
    "reward_unit": "VEs",
    "ledger_status": "posted",
    "new_wallet_balance_snapshot": 145.00
  }
}
```
- **Field-Level Validation**:
  - `reward_id`: String, Mandatory, `^RWD_[0-9]{5}$`.
  - `amount`: Numeric, Mandatory, Strictly positive (`> 0.00`).
  - `ledger_status`: Enum, Mandatory, Must equal `'posted'`.
- **Acceptance Test**:
  > *Under no circumstances may a `reward_credited` event be emitted without an atomic corresponding debit/credit entry in the core ledger journal. Re-triggering must be blocked by `reward_id` uniqueness.*

### Specification DEV-EVT-005: `withdrawal_requested`
- **Requirement ID**: `REQ-ANALYTICS-005`
- **Priority**: Critical
- **Event Name**: `withdrawal_requested`
- **Trigger**: User submits payout cash-out form in the mobile or web wallet interface.
- **Event Source**: Withdrawal Microservice / Ledger Gateway
- **Why Needed**: Initiates payout operational pipeline; locks user balance in escrow; starts SLA turnaround clock.
- **KPI Dependency**: Withdrawal Request Volume, Cash-out Demand, Backlog Queue.
- **Timestamp Standard**: UTC ISO 8601 recorded at form submission.
- **Deduplication Strategy**: Generate unique `withdrawal_id` (`WDR_[0-9]{4}`); enforce 60-second client submission lockout.
- **Payload Schema**:
```json
{
  "event_id": "7b21901a-8c34-4e12-b912-3a8129c01f82",
  "event_name": "withdrawal_requested",
  "timestamp": "2026-05-10T14:00:00.000Z",
  "user_id": "USR_00001",
  "device_platform": "Android",
  "properties": {
    "withdrawal_id": "WDR_0001",
    "requested_amount": 1000.00,
    "currency_unit": "VEs",
    "withdrawal_method": "PayPal",
    "fee_amount": 20.00,
    "destination_account_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "user_kyc_status": "verified"
  }
}
```
- **Field-Level Validation**:
  - `requested_amount`: Numeric, Mandatory, `>= 500.00` (platform minimum payout threshold).
  - `withdrawal_method`: Enum, Mandatory, `IN ('PayPal', 'Crypto_USDT', 'GiftCard_Amazon', 'BankTransfer')`.
  - `destination_account_hash`: String, Mandatory, SHA-256 hash (never raw email or bank numbers).
- **Acceptance Test**:
  > *When a user requests a withdrawal, requested funds must be atomically moved from available balance to escrow balance. If the user's available balance is less than `requested_amount`, the API must reject the request with HTTP 400 and emit zero events.*

### Specification DEV-EVT-006: `withdrawal_completed`
- **Requirement ID**: `REQ-ANALYTICS-006`
- **Priority**: Critical
- **Event Name**: `withdrawal_completed`
- **Trigger**: External payment gateway (PayPal, BitPay, Tremendous) returns HTTP 200 or successful webhook settlement confirmation.
- **Event Source**: Payment Gateway Webhook Connector
- **Why Needed**: Confirms financial settlement; closes payout queue ticket; fulfills user trust promise.
- **KPI Dependency**: Completed Withdrawal Rate, Average Processing Duration (TAT), Payout Volume.
- **Timestamp Standard**: UTC ISO 8601 recorded at webhook receipt.
- **Deduplication Strategy**: Enforce database uniqueness on `withdrawal_id` and payment rail `payout_reference_hash`.
- **Payload Schema**:
```json
{
  "event_id": "1e928b34-4f01-4921-9812-4c8102a91e45",
  "event_name": "withdrawal_completed",
  "timestamp": "2026-05-11T10:15:00.250Z",
  "user_id": "USR_00001",
  "device_platform": "Android",
  "properties": {
    "withdrawal_id": "WDR_0001",
    "settled_amount": 1000.00,
    "currency_unit": "VEs",
    "withdrawal_method": "PayPal",
    "payout_reference_hash": "HASH_9B8C123F",
    "total_processing_duration_seconds": 72900,
    "external_rail_fee_usd": 0.45
  }
}
```
- **Field-Level Validation**:
  - `withdrawal_id`: String, Mandatory, Must match an existing `withdrawal_requested` record.
  - `payout_reference_hash`: String, Mandatory, Non-empty cryptographic settlement proof.
  - `total_processing_duration_seconds`: Integer, Mandatory, Must be `> 0`.
- **Acceptance Test**:
  > *Upon receiving payment confirmation, the withdrawal status must transition to `completed`, locked escrow funds must be permanently burned/debited, and an immutable `withdrawal_completed` event emitted. Repeated partner webhooks must be acknowledged with HTTP 200 but deduplicated.*

### Specification DEV-EVT-007: `referral_converted`
- **Requirement ID**: `REQ-ANALYTICS-007`
- **Priority**: High
- **Event Name**: `referral_converted`
- **Trigger**: Referred user completes their first validated task, passes anti-collusion fraud checks, and the referral bounty is posted to the referrer.
- **Event Source**: Referral Attribution Engine
- **Why Needed**: Confirms genuine viral customer acquisition; triggers referrer reward; calculates viral K-factor.
- **KPI Dependency**: Referral Conversion Rate, Cost per Activated Referee, K-Factor.
- **Timestamp Standard**: UTC ISO 8601 recorded at bounty posting.
- **Deduplication Strategy**: Enforce single conversion per `referral_id`.
- **Payload Schema**:
```json
{
  "event_id": "5f812034-9e12-4b89-8921-2c9182a01d78",
  "event_name": "referral_converted",
  "timestamp": "2026-02-11T11:20:00.100Z",
  "user_id": "USR_00001",
  "device_platform": "Android",
  "properties": {
    "referral_id": "REF_0001",
    "referring_user_id": "USR_00001",
    "referred_user_id": "USR_00025",
    "qualifying_task_activity_id": "TSK_000085",
    "bonus_reward_id": "RWD_000312",
    "bonus_reward_amount": 250.00,
    "reward_unit": "VEs",
    "invite_channel": "WhatsApp"
  }
}
```
- **Field-Level Validation**:
  - `referring_user_id` != `referred_user_id` (enforce anti-self-referral constraint).
  - `qualifying_task_activity_id`: Mandatory FK pointing to validated task.
- **Acceptance Test**:
  > *A referral conversion may only fire when the referee has completed a validated earning activity. If a user refers themselves via the same IP/device fingerprint, the anti-fraud rule must block conversion and flag the referral record as `rejected_collusion`.*
